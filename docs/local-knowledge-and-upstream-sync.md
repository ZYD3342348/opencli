# Local Knowledge And Upstream Sync

> 最后更新：2026-03-28
> 适用仓库：`/Users/zengyuntan/python/opencli`

## 先看结论

如果以后继续从 GitHub 上游拉更新，确实有可能把本地经验覆盖掉，但不是没法防。

这次我们采用的可长期使用方案是三层保护：

1. 代码层：本地保留已经验证过的实现
2. 文档层：把关键经验单独写进低冲突文档
3. 入口层：用 `AGENTS.md` 告诉新的 AI 先读什么、什么不能改

只要这三层都在，后面即使上游代码变化，AI 也能很快知道“这块以前踩过什么坑，什么才算真的成功”。

## 为什么不把经验只写在代码里

只写在代码里有两个问题：

- 上游一旦改同一段实现，冲突最大，最容易被覆盖
- 新开的 AI 上下文未必先读到那段代码，更未必知道哪一版是经过真实验收的

所以关键经验必须再单独落盘，而且文件位置要固定、好找、低冲突。

## 当前推荐的保留方式

### 1. 真相源文档

固定文件：

- `docs/wechat-chatbot-export-source-of-truth.md`

这个文件只记录会影响后续判断和交付的事实，例如：

- 当前稳定链路是什么
- 哪些方案已经证明不稳定
- 什么才算验收成功
- 有哪些真实证据

### 2. AI 入口文件

固定文件：

- `AGENTS.md`

这个文件负责把新来的 AI 直接引导到真相源，不让它从 README 或历史猜。

### 3. 本地分支或 fork

推荐做法：

- 把这批本地经验保留在自己的长期分支里
- 后续拉上游时，优先把上游合进自己的分支
- 不要反过来让本地直接硬覆盖上游再失去比较依据

## 推荐同步流程

以后需要跟 GitHub 上游同步时，建议按这个顺序：

1. 先看 `AGENTS.md`
2. 再看 `docs/wechat-chatbot-export-source-of-truth.md`
3. 拉取上游更新
4. 对比上游是否改到：
   - `src/clis/wechat-chatbot/export.ts`
   - 浏览器桥接相关代码
   - 命令策略定义
5. 如果冲突落在导出链路，不要先看谁更新得新，先看谁有真实验收证据
6. 保住当前已验证事实，除非新的真实证据更强

## 什么情况下要更新真相源

满足下面任一情况时，就应该更新文档，而不是只改代码：

- 稳定导出链路变了
- FAQ 重新变得稳定了
- 验收标准变了
- 新发现某个“看起来成功，其实失败”的假阳性
- 真机验证新增了关键证据

## 给未来 AI 的最短接管路径

如果是一个全新的上下文，最快接管顺序应当是：

1. 读 `AGENTS.md`
2. 读 `docs/wechat-chatbot-export-source-of-truth.md`
3. 再读 `src/clis/wechat-chatbot/export.ts`
4. 最后跑：

```bash
npm test -- src/clis/wechat-chatbot/export.test.ts
npm run build
```

如果要做实机验收，再额外确认：

- 导出 URL 真实可下载
- CSV 非空

## 不建议的做法

- 不建议把这类本地经验只写进 README 主文档，冲突大、噪音大
- 不建议只靠聊天记录保留经验，后面不可复查
- 不建议把“拿到 URL”直接当作成功
- 不建议在没有新证据时反复切换 `batchDownload` 和 FAQ 默认方案

## 最后一句原则

以后如果上游代码和本地经验冲突，先问一句：

“哪一边有更新鲜、可复查、真实非空 CSV 的证据？”

谁有这类证据，谁优先。
